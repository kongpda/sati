# Whole-project review, 2026-11-12: findings and consolidation plan

The owner asked for a deep review of every surface (board, CLI, core, MCP, docs): what is broken, inconsistent, inefficient or no longer needed, what should be merged, separated or removed. The certain bugs were fixed the same day. This file holds everything else, as work packages with a plan and a checklist each. PLAN Phase 11 tracks the packages.

## How to use this file

1. Read `AGENTS.md` first. Its rules apply to every package here.
2. Take one work package (WP) at a time, in the order under "Order of work". Create a sati task for it, claim it, and tick the boxes here and the matching box in PLAN Phase 11 in the same commit as the work.
3. **Verify before you fix.** Each item has a confidence: *certain* (reproduced, or plain from the code), *likely* (read from the code, not run), *unsure* (may be intended). The findings come from three read-only audit passes; only the items under "Already fixed" were confirmed with a failing test. For *likely* and *unsure*, write the failing test or reproduce it first. If it does not fail, tick the box with "not a bug" and one line of why in `docs/progress.md`.
4. Items marked **Owner decision** are listed in "Decisions needed". Each has a recommendation. Do not start one until the owner has answered it there.
5. Every fix gets a test that says why the behaviour matters. Every user-facing change gets a changeset. Every removal gets a `decision_record` and a `feature_check` first.
6. Line numbers are from commit `370b86e` and will drift. Search for the named symbol.

## Summary

- **The core is sound.** Tasks and claims, features and the guard, decisions, notes, file cards, recall and the brief are each used and each do a distinct job. Nothing in the domain is dead weight.
- **The bloat is in the surfaces, not the model.** The board has 11 pages for 3 record families. The CLI has about a dozen duplicate or thin-wrapper commands and uses different flag names for the same idea. The MCP server uses different words from the CLI for the same record (`roadmap` and `milestone`, `context` and `card`).
- **The worst daily pain is approval.** 52 tasks wait in "Waiting for approval" and the board has no way to approve more than one at a time.
- **Performance is within every budget today.** Several services read whole tables where a filter would do. They are listed so the cost does not grow unseen.

## What to keep, merge, separate and remove

### Keep as is (the brain)

| Part | Why it stays |
| --- | --- |
| Tasks, claims, leases, checklist, effort | The unit of work and the only safe way for several agents to share a backlog |
| Features, paths and the guard (`feature_check`, pre-commit) | The one thing no other tracker does: it stops an agent removing shipped work |
| Decisions | The record of why; the guard needs one to remove a shipped feature |
| Notes, comments, handoffs | How agents and people talk across sessions |
| File cards (`context_get`/`context_put`) with staleness | Saves re-reading files; distinct from notes because they are keyed by path and hash |
| `recall` and `search` | Different jobs: a ranked, token-capped answer and an exact search |
| `brief`, `inbox`, `next` | The entry points agents are told to use |
| `changes` and `activity` | Different readers: a changelog for people and an audit log for undo |
| Locks, worktree overlap | Coordination between parallel agents |
| Sync snapshot and merge driver | The team transport |
