The owner asked for a deep review of every surface (board, CLI, core, MCP, docs): what is broken, inconsistent, slow or no longer needed, and what should be merged, separated, removed or redesigned. The certain bugs were fixed the same day. This file holds everything else as work packages. PLAN Phase 11 tracks the packages.

**Second pass (same day).** Every item below was checked again against the code at commit `7e1d00e` by three read-only passes (board, CLI, core and MCP). Items that turned out wrong were corrected or closed (see "Closed without a change"). The owner asked the reviewing agent to make the open decisions; they are recorded under "Decisions". Two packages were added at the owner's request: a board redesign (WP15) and a CLI code refactor (WP16), plus a small foundations package (WP0) that other packages depend on.

## How to work a package

This section is for the agent that implements a package. Read `AGENTS.md` first; its rules win over this file.

1. **One package at a time**, in the order under "Order of work". Inside a package, one item per commit unless the item says otherwise.
2. **Start:** `sati_brief`, then create one sati task per package (or per item for large packages), `task_claim` it.
3. **Before you touch code:** `feature_check` the paths you will delete, move or rewrite. `lock_acquire` shared files (`packages/ui/src/app.tsx`, `packages/cli/src/runtime.ts`, `packages/core/src/ports/storage.ts`).
4. **Verify before you fix.** Each item has a status:
   - *verified*: read in the code or reproduced on 2026-11-12. Still write the failing test first.
   - *verify first*: a part of the item was not confirmed. The item says which part. Confirm it before you change anything. If it does not hold, tick the box, write "not a bug" and one line of why in `docs/progress.md`.
5. **Tests say why.** Each item names a test file and a test name. The name states the reason the behaviour matters. A test that still passes when the rule is broken is wrong.
6. **Line numbers drift.** They are from commit `7e1d00e`. Search for the named symbol.
7. **Gate before every commit:** `pnpm build && pnpm lint && pnpm typecheck && pnpm knip && pnpm test`. CLI tests run against `packages/cli/dist`, so build first. Board changes also run `pnpm test:ui` (the Playwright suite in `e2e/ui`). Performance items also run `pnpm bench`.
8. **In the same commit:** tick the box here, tick the PLAN Phase 11 box when the package is complete, add a changeset (`pnpm changeset`) for anything a user can see, and update the docs the item names.
9. **Record why:** `decision_record` for every removed page, hidden or moved command, and rejected approach.
10. **Finish:** `task_complete` with the claim token, a summary and the files touched. End with what was done, what was verified and what is left.
11. **Never:** `--no-verify`, hand edits under `.sati/` (except `.sati/templates/`), features that are not in this file or `PLAN.md` (put ideas in `docs/ideas.md`), a new dependency without an ADR.

Useful facts for every package:

- Core writes go through `ctx.store.write(async (w) => ...)` with `insertWithLog` / `updateWithLog` (`packages/core/src/services/context.ts`). That gives one transaction and one activity row.
- A new storage port method needs five edits: `packages/core/src/ports/storage.ts`, `packages/store-sqlite/src/store.ts`, `packages/core/test/support/memory-store.ts`, the `METHODS` list in `packages/store-sqlite/src/remote.ts` (bump `PROTOCOL` when a signature changes), and a case in `packages/core/test/support/store-contract.ts`.
- The next migration is `0008_*.sql` in `packages/store-sqlite/drizzle`. Register it in `drizzle/meta/_journal.json`, run `pnpm db:generate`. Hand-written SQL needs `--> statement-breakpoint`. Do not grep `migrations.gen.ts` (it is huge).
- Snapshot format: `EMPTY_FIELDS` in `packages/sync/src/format.ts` is frozen. Adding a field is allowed; changing one is not.
- Core test setup: `packages/core/test/support/setup.ts` `setup()` returns `{store, clock, ctx, project, actor}`.
- CLI test helpers: `packages/cli/test/helpers.ts` has `run(cwd, args, env?, input?)`, `sati(cwd, ...args)`, `satiJson(cwd, ...args)`, `tempRepo({init?})`.
- Board e2e: nav links are clicked with `getByRole("link", { name, exact: true })`; a card is selected with `getByRole("button", { name: "Select <title>" })`; `e2e/ui/a11y.spec.ts` holds a list of every page path (about lines 50-59) and runs axe on each.

## Summary

- **The core is sound.** Tasks and claims, features and the guard, decisions, notes, file cards, recall and the brief are each used and each do a distinct job. Nothing in the domain is dead weight.
- **One real security-relevant bug was found in the second pass.** The guard's shell parser loses the rest of a command after an escaped quote, so `echo "a \"b\"" && rm src/x.ts` is not seen as a delete. It is item 0.1 and goes first.
- **The bloat is in the surfaces, not the model.** The board has 11 pages for 3 record families. The CLI has about a dozen duplicate or thin-wrapper commands and uses different flag names for the same idea. The MCP server uses different words from the CLI for the same record.
- **The worst daily pain is approval.** About 50 tasks wait in "Waiting for approval" and the board has no way to approve more than one at a time.
- **Performance is within every budget today.** Several services read whole tables where a filter would do. They are listed so the cost does not grow unseen. Measure before each change.
- **The two largest files on each surface carry too much.** `packages/ui/src/app.tsx` and `pages.tsx` are 1254 lines each; `packages/cli/src/runtime.ts` is 937 lines and mixes six jobs. WP15 and WP16 split them before the surface work lands in them.

## Decisions

Made on 2026-11-12. The owner asked the reviewing agent to choose "the best recommendation and best practices" for a result that is complete, stable and good to use. Each choice has its reason. An implementing agent treats these as settled; if the code shows a decision cannot hold, stop and write why in `docs/progress.md`.
